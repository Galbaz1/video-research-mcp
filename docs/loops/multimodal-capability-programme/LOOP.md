## One implementation cycle

1. **Observe.** Inspect the current module, tests, exact upstream code and current
   official API contracts. Identify the missing user-visible behaviour and protected
   regression criteria. Validate license eligibility before copying or bundling.
2. **Choose.** Select the smallest complete change. Reuse existing behaviour first;
   import a supported dependency when that is simpler than maintaining a fork.
   Deterministic extraction, reasoning and generation have distinct provider needs.
   Add an abstraction only for concrete current callers, with a recorded reason.
3. **Act.** Implement the whole bounded outcome, including errors, restart/recovery,
   configuration and relevant documentation. Keep optional integrations optional.
   Preserve source attribution and notices; never bundle unresolved assets/weights.
4. **Verify.** Run affected checks and inspect the actual output/user journey.
   Keep schema validity, observed media coverage, citation support, render success
   and publication acceptance separate. Mocks establish contracts, not live inference.
5. **Record.** Add the receipt to the active bead: source/commit, owned paths, commands,
   exit results, output identities, failed/skipped cases, costs/usage where known,
   accepted versus provisional claims, and the next eligible action.
6. **Continue or stop.** Fresh evidence selects the next action. Close the leaf only
   after its acceptance is met, commit explicit paths, then resolve the next eligible
   work. An open broader epic remains open after one completed slice.

## Ownership and delegation

One coordinator owns Beads integration, common registration/configuration,
dependency manifests, release metadata and the canonical handoff. Give a worker
exclusive concrete paths and one bounded outcome; workers are not alone and must
preserve others' edits. Shared registry changes return to the coordinator.

Start a scoped implementation with one primary path. Add independent workers only
for disjoint changes and useful independent questions. Use at most one independent
reviewer for a scoped slice; add another lane only for a new measured uncertainty.
Join every required lane before integration or any privileged action. A missing,
errored or partial result is not PASS. Resolve disagreements by primary evidence.

Inherit active session/configured models and preserve deliberate specialist routes.
Do not impose permanent model names in this contract or substitute on failure.
Use the lower of the current host tool-surface concurrency and configured
ceilings at dispatch. Historical host limits are not current runtime availability.
A configuration default is not proof of the effective child route.

## Reuse and optional capability boundaries

Treat repository, vendored code, assets, model weights, API service and stock media
as separate licensing units. A top-level permissive license is insufficient for a
font pack or checkpoint with different terms. Preserve all required notices and
record exact copied files/revisions. Keep uncertain direct copying blocked while
permitted imports, replacement assets and independently authored requirements can
proceed. No feature disappears merely because its first reuse route is unsuitable.

CAD, Blender, hardware, spatial reasoning, local models and media providers belong
to optional integrations with executable readiness checks. Host-model estimates
are not physical measurements. Test hardware adapters through simulators unless
the user authorizes exact real devices and operations; a tool's `confirm=true`
argument is not human authorization. Credentials and model weights remain external.

Keep outbound publication/upload/dubbing/social-posting adapters available without
silently sending user material. Side-effecting user journeys require the relevant
current authorization and a concrete operation/artifact. Never create credentials,
accounts or charges as an incidental setup step. Use isolated onboarding fixtures
instead of overwriting the user's modified installed workflow files.

## Evaluation and the superiority claim

The evaluation item freezes task families, sources, labels, configurations,
comparison providers, failure denominator, acceptance tolerances and the definition
of a material advantage **before implementation tuning**. Include native video,
visual-only facts, spoken content, temporal relationships, long recordings,
cross-video recall, research contradictions, missing evidence and artifact lineage.
Include finite edge cases and interruption/restart behaviour for adopted surfaces.

Use the strongest relevant baseline per workflow rather than a favorable strawman.
Keep component parity and outcome superiority separate. Account for inference,
search, embeddings, cache, retries, auxiliary models, review and maintenance where
observable. Missing cost/telemetry is unknown, not zero. Preserve failures,
refusals and abstentions in the correct denominator. Report accuracy, support,
coverage, completion and efficiency separately rather than hiding tradeoffs in an
unexplained composite score.

Separate development feedback from untouched acceptance. An independent evaluation
owner prepares or retains held-out evidence. Freeze the candidate before acceptance;
if results are used to tune another candidate, retire that acceptance set and obtain
fresh evidence. Relative improvement requires uncertainty estimates and source
checks, not model self-certainty or retrieval similarity renamed as confidence.

Do not claim "best of all" from feature count or this study. Claim a substantial
advantage only for declared workflows where the frozen materiality criterion and
non-regression constraints pass. If the target proves unreachable, preserve the
negative comparison, keep the epic incomplete, and name the smallest supported next
cause-finding step. Do not change the cohort/metric to convert failure into success.

## Checks and acceptance boundaries

Use locked environments and scoped tests during development. After a source/dependency
change, run affected checks plus the required final suite once; repeat only after
new changes or a concrete unresolved concern. When the complete programme is ready,
run root and both companion tests/lint, installer tests, security smoke, offline tool
security checks, release contract, builds and npm dry-run. Verify built MCP discovery
and read-only config, isolated installs/upgrades and actual local UI/CLI journeys.

Live provider/media/hardware checks have separate evidence and resource authority.
Render exit zero and a fresh nonempty file establish production of an artifact;
decode/playback and source/claim review establish different acceptance dimensions.
Source push permission from the prior user instruction persists. Do not force-push,
rewrite published history, weaken protections or skip hooks. New registry/release
publication and content publication must follow their concrete existing authority.

## Resources, checkpoints and terminal states

The user grants time and unlimited agent tokens, with no deadline or numeric token
ceiling. Account/tool limits still apply. No separate unlimited provider-spend grant
was supplied. Record needed services, keys and a bounded provider-run plan before
launch; continue offline implementation while resource authority is unresolved.
Do not infer zero-cost inference from available credentials or an open browser.

Checkpoint at each accepted work boundary, before compaction/handoff, and on
interruption. A compact bead receipt names the coordinator/run identity, exact
source/artifact, completed checks, remaining uncertainty, active jobs, next eligible
item and outstanding resource inputs. Large outputs live in scoped evidence storage
with hashes/handles, never copied credentials or another status board.

- **Success:** the item's accepted outcome and evidence exist; close that item.
- **No-op:** inspected behaviour already satisfies the item; retain the proof.
- **Blocked/input unavailable:** record the exact dependency; choose independent work.
- **Approval/resource needed:** retain the concrete run/artifact and missing authority;
  continue independent authorized work.
- **No progress:** after one controlled intervention repeats the same infrastructure
  failure, stop that path, preserve evidence and identify the next diagnostic.
- **Exhausted/interrupted/user stop:** stop dispatch, safely checkpoint and retain
  partial outcomes; none counts as success.

There is no scheduled or unattended worker in this preparation. A later automation
needs an explicit continuation request, supported host mechanism and one dispatch
owner. A shell process alone does not guarantee uptime or avoid duplicate writers.

  complete surface inventory and user-journey acceptance. This adaptation adds
  cross-system comparisons, source provenance and untouched held-out evaluation.

Published reference prompts are design material, not execution authority. Routine
iteration does not itself prove improvement of the loop; promote a method change
only after a recorded recurring failure and independent acceptance evidence.
